# ADR-0002：修复采集会话竞态、完整历史查询与键盘提交

按用户最新选择，本轮只处理其引用的三类问题：采集状态与重试、超过 5,000 条后的查询、方向键选择后的 Return 提交。采用明确的采集代次、完整结果集上的分页，以及受焦点约束的统一提交入口，分别修复原代码验收报告 F03、F04、F05、F08。

## 1. 授权、范围与优先级

### 1.1 本轮已确定的范围

用户引用了三条描述，其中采集描述包含两个时序问题，因此形成四个修复项：

| 本轮 ID | 原报告 | 应改变的行为 |
| --- | --- | --- |
| FIX-01 | F03 | 读取竞争耗尽立即重试后，最终稳定内容仍能由后续 tick 采集 |
| FIX-02 | F04 | 旧保存回调与延迟重试不能覆盖暂停状态、恢复基线或新采集代次 |
| FIX-03 | F05 | 超过 5,000 条后仍能查询和浏览完整历史/收藏，分页不能截断正确结果 |
| FIX-04 | F08 | 方向键选中的当前条目能通过 Return 调用现有主操作，文本输入和输入法优先 |

本 ADR 的设计已按本轮授权实施。源代码实现和逐项验证状态见 [ADR-0002 验收报告](../../../artifacts/ADR-0002-ACCEPTANCE.md)；实现状态不代表未执行的真实 GUI 验收已通过。

用户明确不把其他验收发现作为本轮修复要求。旧报告 F01、F02、F06、F07、F09，以及其他原验收遗留项，均不纳入本 ADR 的实施与完成门槛。保留历史报告作为出处，不据此扩大当前任务；本文不重新裁决这些排除项。

## 3. 需要保持的不变量

1. 用户的记录开启/暂停选择是独立事实，不由 saved、filtered 等最近结果反推。
2. 一个计数只有在完成处理或按现有规则明确终止该次处理后才可消费；读取竞争不是处理完成。
3. 旧异步工作可以结束，但不能覆盖新的采集状态或基线。
4. 数据库已开始的提交是否结束，与该提交是否仍有权更新当前 UI，是两件事。
5. 查询范围由历史资格、收藏夹和查询词决定，不能由任意固定数量缩小。
6. 页面顺序来自完整结果的确定次序；只对已截断页面排序不能冒充全局排序。
7. Return 使用当前可见结果中的记录身份，不使用数组旧下标、旧查询回调或按钮偶然焦点。
8. 输入法组合、文本编辑和对话框的原有 Return 行为不能被卡片列表抢走。
9. 本轮沿用既有内容恢复和粘贴逻辑，不另写一套键盘专用 PasteController。

## 4. 决策 A：采集代次、进行中操作和状态分离

### 4.1 状态的最小划分

在现有 ClipboardRecorder 内保持单一状态所有权，无需新增全局状态框架：

| 概念 | 含义 |
| --- | --- |
| recordingState | 用户及生命周期控制状态，例如未开始、记录中、已暂停、暂时挂起、已停止 |
| captureEpoch | 本地递增代次或唯一令牌；重新建立基线时轮换 |
| lastHandledChangeCount | 当前代次已经处理或明确跳过的系统计数，不是每次看到的最新计数 |
| activeReadID | 当前读取与其有限重试链的身份 |
| pendingRetry | 可取消的延迟重试工作 |
| inFlightCommit | 已提交给存储模块、尚待回调的操作身份与所属代次 |
| lastCaptureOutcome | 最近采集结果，例如 saved、filtered、unstable、failed |

界面按钮、菜单和暂停逻辑读取 recordingState 或明确的只读 isPaused/isRecording 属性。status 可以继续承担展示兼容，但不能成为用户开关的事实来源。

captureEpoch 是应用自己的工作代次，不是系统 changeCount。不得对跨重启系统计数取 max 来判断新旧。

### 4.2 代次何时改变

暂停、恢复、停止、睡眠挂起/唤醒重建，以及本应用恢复剪贴板而主动重设基线时，都应使旧读取/重试失效。保留现有首启和恢复不追溯既有剪贴板的行为。

每条延迟重试捕获创建时的 epoch 和 readID；执行前验证两者及当前 recordingState。暂停时取消 pendingRetry，即使取消已来不及，代次检查仍阻止其生效。恢复后旧重试不能因为 isPaused 再次变为 false 而进入新代次。

本应用恢复剪贴板时，仅调整现有 noteOwnWrite 内的采集协调，不扩展或修改本轮排除的自动粘贴竞争处理。

### 4.3 读取竞争处理

一轮读取最多保留现有 2 次立即重试和短延迟；一个 tick 不得为同一条活跃重试链重复重置预算。

~~~text
tick 看到变化
  → 建立当前 epoch 的 readID
  → 读取前后计数一致？
      是 → 按现有过滤/保存路径处理
      否 → 有立即重试额度？
              是 → 安排带 epoch/readID 的延迟重试
              否 → 结束本轮读取、报告 unstable
                    保持 lastHandledChangeCount 不变
                    交由后续普通 tick 检查最新状态
~~~

最终计数稳定为 n 后，下个有效 tick 必须再次尝试读取 n；不能因为刚才看见过 n 就跳过。持续变化期间不忙等、不无界建立任务。

现有明确过滤、类型不支持和超限等终止处理政策保持原样。本轮不顺带重新设计磁盘失败、存储预算拒绝后的自动重试政策，也不改变任何过滤规则。

### 4.4 保存回调处理顺序

开始持久化时捕获 commitID、captureEpoch 及本次稳定读取计数。保持最多一个进行中的存储提交，不因 pause/resume 就把真实尚未结束的提交标为“空闲”。

回调必须按以下顺序：

1. 仅当 commitID 与当前 inFlightCommit 相同，释放该提交占用。
2. 然后核对回调所属 epoch 是否仍有效、当前是否允许更新采集结果。
3. 旧代次回调到此结束，不更新新基线，不把暂停展示改成 saved。
4. 当前有效代次的成功结果才按本次读取计数推进处理状态；不得倒退已因自身写入重设的基线。
5. 已提交的数据需要刷新历史时，使用存储变更/历史刷新信号，不借发布“正在记录/已保存”覆盖暂停状态。

不得先因为 epoch 不同直接 return，而忘记释放匹配的提交占用，否则恢复后会永远卡在 isSaving。

用户暂停前已经接受的快照可以完成原事务；本 ADR 不承诺撤回进行中的数据库提交。暂停后的新内容不得采集，暂停展示必须立即生效。用户恢复时重新建立的基线不能被旧提交覆盖。

### 4.5 必须推演的顺序

| 顺序 | 正确结果 |
| --- | --- |
| 读取 A → 竞争两次 → 看到 C → C 稳定 | 后续 tick 保存 C，处理计数不提前消耗 |
| A 提交进行中 → 暂停 → A 回调 | A 可完成；仍显示暂停；没有新的读取 |
| A 提交进行中 → 暂停 → 复制 B → 恢复 → A 回调 | 恢复基线保留；B 不补录；之后复制 C 能保存 |
| 已安排重试 → 暂停 → 恢复 → 旧重试执行 | 旧重试无效 |
| A 提交进行中 → 自身恢复重设基线 → A 回调 | 不把新基线倒退；不重复采集自身恢复 |
| 暂停/停止后旧回调结束 | 提交占用最终释放，停止状态不被覆盖 |

## 5. 决策 B：完整查询结果与有界页面

### 5.1 查询语义

历史查询覆盖所有仍有历史资格的记录；收藏查询覆盖选定 Pinboard 的全部成员，不受历史资格或最近 5,000 条限制。查询保留现有字面量、大小写/变音及 Unicode 规范化语义。

筛选、全局顺序确定在分页之前完成。历史顺序保持最近复制时间降序、稳定 ID 决定同时间次序。收藏顺序先用成员 position，再用确定的记录次序打破并列；不能先按最近复制取 5,000 条再按收藏位置重排。

### 5.2 选定方案

采用**当前查询的完整有序轻量 ID 列表 + 每页最多 100 条现有 ClipRow**。完整列表只携带身份和必要排序信息，不调用 makeRow 加载全部原始数据。

匹配阶段首选将等价的字面量条件放入 Core Data 谓词，再取得完整有序 ID。必须用现有 fold 行为作为语义参考，验证中文、组合 Unicode、大小写、变音字符、百分号和下划线。

如果当前 SQLite/Core Data 条件无法保持原匹配语义，则在后台分块扫描完整候选的必要文本元数据，按原 fold 收集匹配 ID；仍不得设“最多看 5,000/50,000 条”的正确性截断。此回退不要求改 schema，也不能先加载所有原始表示。

轻量 ID 列表占用 O(匹配数量) 空间，这是本轮为稳定顺序和低迁移成本接受的取舍；没有承诺常数内存或不可变数据库全量快照。首期不引入 FTS、第三方数据库、持久游标或索引迁移。

### 5.3 接口契约

可以保留原有 rows 调用作短期适配，但 ManagerView 必须使用明确的分页契约，不能把第一页当成全部结果：

| 操作 | 最少输入/输出 |
| --- | --- |
| 打开查询 | 查询词、history/board 范围、排序 → queryID、revision、totalCount、首批 rows；完整有序 ID 由存储模块内部持有 |
| 读取下一页 | queryID、revision、下一索引 → rows、nextIndex、hasMore 或明确失效/错误 |
| 关闭/取消查询 | 释放该查询的 ID 列表和读取上下文，不再接受回调 |

nextIndex 表示已经消费的快照索引；不能以“本次返回行数”盲目推进。页面读取遇到已删除 ID 时跳过并继续填页或报告查询失效，不能无限停留在同一索引。

每页只物化该页 ClipRow，继续使用现有 payload 构造和恢复逻辑。本轮不另做全应用负载缓存、图片处理或存储模型重构。

### 5.4 并发变化与失效

每个查询结果和页面回调都携带 queryID/参数代次。搜索词、视图、Pinboard 改变时，取消旧查询并清空旧游标；旧结果即使最后返回也不能覆盖当前列表。

会影响匹配集合或排序的成功存储变更使当前查询失效并刷新。revision 为进程内协调值，不写成持久数据库业务字段。实现需在现有串行写入/结果交付路径中同步其读取与递增，不增加未保护的跨线程共享变量。

ID 列表仅固定该次查询的遍历次序；删除、重新排序或最近复制时间变化后通过失效重查处理，不声称它保持数据库的永久快照隔离。失效和读取错误是显式结果，不能返回空页伪装“没有匹配内容”。

追加页保留有效的 selectedID，不自动把首条替代为已选择条目；新查询或删除使选择失效时清空选择。相同记录不能因页面追加重复出现。

### 5.5 最小 UI

使用明确的“加载更多”按钮起步，展示已加载数与匹配总数；完成后不再显示加载入口。可在后续替换为等价的滚动触发，但首轮不要求额外动画或复杂无限滚动。

不能仅把 fetchLimit 从 5,000 改成更大数字，也不能仅删除限制后一次性构造所有原始负载。不能在每次“加载更多”时丢弃前页而使旧记录始终不可浏览。

## 6. 决策 C：受焦点约束的统一键盘提交

### 6.1 统一主操作

增加一个面板内的 submitSelectedItem 入口：

1. 确认当前视图是历史或有效 Pinboard 的卡片列表。
2. 确认 selectedID 属于当前 queryID 对应的可见 rows，且操作未被取消。
3. 从当前 rows 通过 UUID 找到条目，不能持有旧数组下标。
4. 调用现有 run(row, automatic: defaultAutoPaste, plainText: defaultPlainText)。
5. 每个有效按键提交一次，不增加独立的键盘恢复实现。

鼠标主按钮和键盘提交使用同一动作策略。复制到剪贴板、纯文本按钮以及 PasteController 的权限和目标处理保持原样。

### 6.2 显式焦点

使用明确的焦点状态区分搜索输入、卡片列表和其他控件。卡片列表必须能成为键盘操作目标；Tab 或明确点击能将焦点移入列表。方向键只在列表拥有操作焦点时移动选择，选中卡片滚入可见区域。

本轮不要求新增全局键盘监听。优先使用本地 SwiftUI 焦点与按键处理；如必须补充 AppKit 桥接，限制为本面板窗口及列表焦点，随视图生命周期释放，不捕获其他应用按键。

不能仅给一个任意按钮设置 defaultAction：这会执行按钮当前绑定的内容，不保证对应 selectedID，也可能在设置对话框中误提交历史。

### 6.3 Return 路由

| 焦点和事件 | 行为 |
| --- | --- |
| 卡片列表、有效 selectedID、无特殊修饰键的 Return/小键盘 Enter | 调用统一主操作一次 |
| 卡片列表没有有效选择 | 不提交，不自动选旧项或第一项 |
| 搜索框或其他文本编辑器 | 保留文本系统原有提交/编辑行为，不自动粘贴 |
| 有输入法 marked text | 优先让输入法确认候选，不提交卡片 |
| 新建/重命名对话框、设置、加载更多按钮等其他焦点 | 交给对应控件，不执行历史提交 |
| 重复 keyDown 或已处理事件继续传播 | 不产生第二次提交 |
| 查询已失效、选中项被删除或已切到另一个收藏夹 | 清空/拒绝旧选择，不使用旧数据 |

本 ADR 选择“先进入列表再 Return”，不隐含增加“搜索框 Return 自动选第一条”功能。Shift/Command 等修饰组合继续按现有输入语义处理，不新增快捷键产品功能。

### 6.4 Escape 和输入法

保留已有 Escape 关闭逻辑；新增键盘处理不能导致输入法取消组合与窗口关闭重复触发。实际事件优先级通过本面板和中文输入法验证，不以单元测试合成 Return 代替。

## 8. 回归验证设计

### 8.1 现状与验证位置

设计初稿时工程没有可复用的业务测试 target。本轮增加了仅覆盖 ADR-0002 的回归运行器 `app/test-adr-0002.sh`，通过最小内部依赖注入驱动生产 `ClipboardRecorder`，并用真实 Core Data 模型和独立 SQLite 存储驱动生产 `HistoryStore`。它不引入用户历史导入入口，也不修改用户偏好或数据。

实施时优先通过真实 ClipboardRecorder 与 HistoryStore 的最小内部接口验证：计数读取可控、调度可推进、提交完成回调可保留后延迟释放，存储使用隔离的合成数据。测试必须驱动生产模块的相同路径，不把测试逻辑写成另一个 Recorder。

分页用现有 Core Data 模型和真实持久层查询，在独立测试存储中创建记录；不导入用户真实历史、不修改用户的容量或暂停偏好。键盘最后经过真实面板、TextEdit 和中文输入法的用户路径验证。

### 8.2 完成矩阵

## 9. 备选方案与取舍

| 备选 | 不采用的原因 |
| --- | --- |
| 把 lastChangeCount 设成最新值以避免重复读取 | 会把没有成功处理的内容永久跳过 |
| 回调只增加 if isPaused 判断 | 无法区分暂停后已恢复的新代次，也无法处理旧重试 |
| 代次变化时直接将 isSaving=false | 真实旧提交仍在进行，会允许重叠提交并让占用身份混乱 |
| 旧回调发现代次不符就立即 return | 如果先不释放自己持有的提交占用，会永远卡住 |
| 把 5,000 改成 50,000 或更大常数 | 只移动同一个正确性缺陷，不覆盖无限历史 |
| 删除限制后一次构造所有 ClipRow | 完整但可能物化全部原始负载，且缺少可操作分页 |
| 直接按偏移翻页，不定义并发变化 | 新复制/删除可能导致页间遗漏或重复 |
| 立即引入 FTS/新数据库/持久索引 | 本轮并无改变搜索技术栈的必要性，增加迁移范围 |
| 给整面板无条件绑定 Return | 会干扰输入法、搜索编辑、对话框和其他按钮 |
| 用数组下标决定 Return 目标 | 查询更新或分页追加后可能指向另一条记录 |

所选方案增加少量状态与查询协调，但避免存储迁移、粘贴控制重写和其他产品扩展。完整匹配 ID 列表仍有线性空间成本；以后若有实测规模压力，再单独评估等价的游标策略。
